## Stack

- Nuxt 4 (`app/` dir), TypeScript strict, Node 24 (`.nvmrc`), **pnpm**
- PrimeVue 4.5.5 styled mode via `@primevue/nuxt-module`; `@primeuix/themes` 2.0.3

## Architecture

- Routes (`routeRules`): `/` prerender (landing), `/docs/**` prerender, `/editor` `ssr: false`, `/preview` `ssr: false` (only ever rendered in an iframe inside `/editor`, no layout).
- Preview isolation: the editor UI uses its own fixed PrimeVue theme. The theme being designed is applied only inside the `/preview` iframe (its own PrimeVue instance) via `usePreset`. Editor → iframe communication is a typed postMessage protocol (`app/utils/theme/messages.ts`) with same-origin checks on both sides. Preview dark mode = `.ps-dark` class on the iframe's `<html>` (`darkModeSelector`).
- Theming model (from the preset source): 3 layers (primitive → semantic → components, ~3k tokens/preset), `{a.b}` references compile to `--p-a-b` CSS vars, light/dark values under `colorScheme` at any layer. Token naming rules live in `tokens.ts`; `tokens.test.ts` checks the resolver against the engine's `$dt` for every token of all 4 presets.
- State (`ThemeState` v2): `basePreset` + `design` (high-level decisions: primary, surface per scheme (built-in, tinted or any custom color), status colors per severity, tinted light backgrounds, radius scale or custom px steps, density preset or custom scale, focus ring; each defaults to `{ kind: 'base' }`/`'base'` = inherit) + raw `overrides` (win last). `build.ts`: `designToTokens` → merge overrides → `definePreset(base, …)`. Design decisions must reach every component in all 4 presets: density scales every literal padding/gap/gutter/margin token, a custom focus outline rewrites every component `focusRing` (except form fields and inset rings), status colors add `primitive.status.<kind>` palettes and repoint chromatic references inside each severity's component tokens (keeping the shade). New optional design fields only need defaults in `parseDesign`; bump the version and add a migration in `serialize.ts` for any other shape change.
- Preview CSS (`preview-css.ts`, `usePreviewForcedStyles`): focus/hover/pressed styles are copied from the stylesheet source text and scoped to classes (`.ps-show-focus`, `.ps-force-hover`, `.ps-force-active`) to show states without interaction; `schemeScopeCss` re-declares the `:root` and `.ps-dark` variables inside `.ps-scheme` areas so light and dark can sit side by side on one page.
- Component studios (`STUDIO_COMPONENTS`: Button, Message, Toast, Tag, Badge): a stage in the preview (`components/preview/stage/`) shows every variant × state in light and dark; the inspector's Design view (`components/editor/studio/`) has purpose-grouped controls. Colors are shared (`VariantColors`); Button's editor is hand-built, severity components (`Severity`) are driven by `studio-controls.ts` (paths checked against all presets by its test), with stages in `components/preview/stage/` sharing `Schemes` (light/dark columns). Recoloring only moves a variant's main palette, so neutral parts (Toast detail text) stay. A variant's palette is changed by recoloring its tokens to another palette at the same shades (`recolor.ts`), so each preset's light/dark shade choices are kept; custom colors generate a palette under `primitive.ps.<component>.<group>`. Clicks on the stage arrive as `preview:stage-pick`. Studio components are listed by name in the sidebar's Components group and pinned in the component list; `editor.openComponent` always opens them in the Design view with their stage. Components built from a studio component with only a few tokens of their own (`STUDIO_FAMILY`: SplitButton, SpeedDial → Button) are edited in that studio's family section; ButtonGroup has no tokens. Foundations and patterns show what they reach with `EditorUsedBy` ("Used by N components" chips, visual editors first), and gallery demos of studio components show a Customize link (sends `preview:inspect`).
- Stores (Pinia, one-way: editor → workspace ← preset). Components use the one(s) they need (`const workspace = useWorkspaceStore()` etc.):
  - `workspace` (`app/stores/workspace.ts`): the saved themes (localStorage, v1 key migrated; tabs share it: every save and every other tab's save (`storage` event) is merged per theme by `mergeWorkspaces`, newest `updatedAt` wins, deletes leave tombstones in `state.deleted`; anything that changes a theme document must bump its `updatedAt`), the open `theme`, snapshot undo/redo per theme with key-based coalescing for drags (kept per theme in this tab's sessionStorage, so it survives reloads; `serializeHistory`/`restoreHistory` in `history.ts`). Change themes only through `workspace.update(mutator, coalesceKey)`; `theme` is deep-frozen in dev so direct writes throw.
  - `preset` (`app/stores/preset.ts`): the open theme as a preset: base preset loading, resolvers (theme and untouched base), descriptors, contrast, counts, export, and token edits (`setToken`, `recolorGroup`, resets). Every edit rebuilds the resolvers, so this is the hot path of drags: `buildEffectivePreset` shares the base preset's untouched subtrees (`overlayTree`) and `flattenPreset` caches per subtree, so preset trees must never be mutated; derived objects and lists that many components read use `stableComputed` (kept while their content is equal) so a drag only re-renders what shows the edited value.
  - `editor` (`app/stores/editor.ts`): UI only: prefs (section, preview options, views; the preview color scheme and section are prefs, not theme data), stage, navigation (`openComponent`, reveal, stage picks, Compare). UI constants (`EDITOR_SECTIONS`, …) live in `app/utils/editor-sections.ts`.
- Search (`EditorSearch`, ⌘K / Ctrl+K): sections, components, tokens (the ones the token lists show for the previewed scheme) and actions, ranked by `app/utils/search.ts`. A token opens the list that holds it (`editor.openToken` → `tokenRequest`, handled by `useTokenRequest` in that list). The preview passes editor shortcuts (search, undo/redo, Escape while picking) to the editor as `preview:shortcut` messages, since key events in the iframe don't reach it.
- Landing page (`pages/index.vue`, prerendered): real PrimeVue components (`LandingSpecimen`) drawn in a theme without an iframe: `specimenVars` (`specimen.ts`) writes every semantic token and the specimen's component tokens out as resolved values on a wrapper (a variable that refers to another resolves where it's declared, so overriding the primary scale alone wouldn't reach the components). The page chrome stays neutral; the visitor's brand color is the only color. The logo is a five-step scale in the colors of the theme on screen (`useLogoColors` sets `--ps-logo-1…5` on `<html>`: the landing page's pick, the editor's open theme); elsewhere, and in the favicon and loading screen, it shows the brand ramp (`BRAND_RAMP` in `utils/logo.ts`, shades of the landing default #0f766e). "One color, all the way down" shows real reference chains (`referenceChain`: palette shade → semantic → component token) for the chosen base preset. "Continue in the editor" goes to `/editor#start=<share token>`: on a first visit the choices go into the untouched theme and the setup opens, otherwise they're offered as a new theme. Example themes (`EXAMPLE_THEMES` in `utils/landing.ts`) open as share links.
- Import and share (`share.ts`): theme files (a JSON envelope `{ format: 'presetstudio-theme', version, name, theme }`) and share links (`/editor#theme=<deflate-raw + base64url>`, the hash never reaches a server). Both are untrusted: decoding is size-limited (512 KB, inflate stops early) and the theme goes through `parseThemeState`. Imports always add a new theme (`workspace.importTheme`), never replace one.
- Token values are untrusted (they end up in CSS custom properties): always pass them through `sanitizeTokenValue`/`sanitizeTokenTree` (`values.ts`); `serialize.ts` does this on load and on postMessage.
- Component tokens: `components.ts` lists every component of the presets (official name, PrimeVue docs category, deprecations); `components.test.ts` fails if a preset gains or loses one. Tokens are grouped by the preset's own top-level parts (root, header, option, primary, outlined…). The preview finds components by PrimeVue's `data-pc-name` (nested instances are `pc*`, reported as "also uses"); on-demand overlays are found through their gallery demo (`data-ps-demo`, derived from the demo title). Inspect mode and reveal live in `usePreviewInspector`.
- Inspector content must never be wider than the panel: flex/grid children that hold long values need `min-w-0` (PrimeVue's AccordionContent is a grid, so it needs a `minmax(0,1fr)` column).
- Editor sections (`EDITOR_SECTIONS`): Overview (`start`: the base style switch; each decision as a tile drawn in the theme's own colors for the previewed mode, one click from its section ("<Base> default, adjusted" when its tokens were edited but the choice wasn't); "Ready to ship?" (contrast with Fix all, changes, and the save status only when it isn't saved); the guided setup (`EditorSetup`, `QuickStartPanel`) asks the first questions); Foundations (primary, surface, status, text, shape, density, focus); Patterns (form fields, lists, menus, overlays, containers, selection: shared looks many components use, each editing one semantic group via `PATTERN_SECTIONS`, with a stage); Components (all + visual editors); Advanced → All tokens (raw semantic list); Review. Each concept has exactly one home: semantic groups that aren't patterns are set by foundations (surface, focus ring, primary's state grid in Primary color) or are part of a pattern (mask → overlays); see `SEMANTIC_ELSEWHERE`.
- UI names differ from code names: foundations are shown as "Look & feel", patterns as "Shared styles", inspect mode as "Pick", the stage switch as "All states | In an app". Use the UI names in anything users read.
- Preview per section (the preview follows the panel): foundations, Text, patterns and visual components have a stage (`stages.ts`: `foundation-*`, `semantic-*`, component names); every section and component also has a page "In an app" (`SECTION_PAGES` in `editor-sections.ts`, a component its gallery category), switched by `editor.previewKey`; a page picked by hand is remembered per section (`prefs.pages`). The preview toolbar never changes shape: All states | In an app, the page, Pick, Light | Dark | Both, View (what doesn't apply is disabled). Light | Dark | Both is the only mode switch: stages follow it (`bothSchemes` in the apply message), panels with per-mode values show `EditorSchemeNote` (which mode they edit, a button that switches the preview), not their own toggles, and panel swatches show that mode (a light | dark pair only with Both: `useShownScheme`). Panel and stage are linked both ways: stage elements carry `v-pick="target"` (`plugins/pick.ts`: tags `data-ps-pick`, clicks become `preview:stage-pick`), panel controls carry `data-stage-target` patterns (`stage-targets.ts`: prefixes, `*` wildcards), and `useStageTargets` (Inspector) sends `preview:highlight` while one is hovered/focused and a pulse after a change. "In an app", `preview:spotlight` dims the components the section doesn't change (`useSpotlightComponents`, the "Used by" lists; containers are never dimmed whole); `EditorPreviewStatus` is a chip shown only while the spotlight dims something, with the way out (the switch is also in the View menu). Clicks in the preview never reach the editor's document, so `editor.vue` closes open menus when focus moves into the preview. The panel's Design | All tokens switch only changes the panel. The base preset is chosen in the setup and in Overview only; the top bar holds the theme menu, the save status ("Saved" in this browser, or "Not saved" when storage is refused: `workspace.saved`), undo/redo and Export, the one way out (its drawer: code for your app, or a share link and the theme file). Nothing else repeats Export.
- Contrast (`contrast.ts`, Review → Accessibility): every failing check counts (`preset.contrastIssues`), the base preset's own included, labelled by where it comes from (your changes or the base). `contrastFix` (applied through `useContrastFixes`, shared by Accessibility and Overview) moves a failing token to the nearest passing shade of its own scale, with its hover/pressed tokens shifted by the same steps; primary button text with no passing shade switches to the most readable text color. Fixes are undoable; one "Fix all" is one undo step.
- Editor UI, two layouts (`prefs.layout`, switched in the top bar's settings menu):
  - `panels` (default): destination rail (`EditorDestinationNav`: Overview, Colors, Shape & spacing, Components, Review; `EDITOR_DESTINATIONS` in `editor-sections.ts`, every section in exactly one, tested) · one panel (`EditorSectionTabs` for the destination's sections in the Inspector's `nav` slot, then the section panel) · preview. Shared styles (patterns) live under Components, All tokens under Review. A destination always opens its first section (Components: the list). There is no title row in this layout, since the navigation names the section (the active tab, or the rail for Overview); a tab carries its section's explanation (tooltip), and Reset closes the panel, shown only when there is something to reset; inside a component the title row has the way back, Show in preview and Reset. Failing contrast checks show as a count on Review (and in Overview), nowhere else. Below `lg` the rail becomes a bar above the panel.
  - `classic`: section nav · preview iframe · inspector; below `xl` the section nav becomes a select in the inspector header.
  - Panels live in `app/components/editor/panels/` and work in both. "Changed" dots come from `useSectionStatus`. Below `lg` the preview is a strip above the controls (its own buttons: full screen, hide; the full preview has Done), and the preview toolbar wraps to two rows.
- Pure logic (color/OKLCH, palettes, resolver, schema, design mapping, merging, export, serialization, history, contrast) lives in framework-free TS modules in `app/utils/theme/` with unit tests next to them (`*.test.ts`). These must not import Vue/Nuxt.

## Conventions

- Commands: `pnpm dev`, `pnpm lint`, `pnpm test`, `pnpm build`, `pnpm license:check`. All four must pass before committing.
- Quiet UI: titles and controls are visible; explanations are on demand (`EditorInfoTip` ⓘ, or `EditorInspectorGroup`'s `description`), not gray paragraphs. Separate with space, not boxes or lines (borders only between panes and under bars). Spacing: 16px pane padding, 24px between groups, 8px inside a group; top bar 48px. Sentence-case labels (no uppercase micro-labels). Show a hint only when it's actionable. A choice that falls back to the base preset is named "<Base> default" (`useBaseDefault`), never "Preset".
- UI: use PrimeVue components for every interactive control (Button, RadioButton, Menu, SelectButton, …), including links styled as buttons (`Button :as="NuxtLink"` / `as="a"`). Native elements only for semantic markup (lists, fieldset, inline text links, the `<a v-bind="props.action">` inside Menu item templates). Shared editor controls: `EditorOptionCard` (radio card), `EditorColorSwatch`.
- The `primevue.importTheme` module must export `{ preset, options }`, not a bare preset (otherwise no CSS variables are generated).
- Conventional Commits, small and logical. Don't push without the owner's review.
- Footer/README disclaimer must stay: "PrimeVue is a trademark of PrimeTek Informatics. Preset Studio is an independent open-source project and is not affiliated with or endorsed by PrimeTek."
